# 8.1 How this book is written

> **Status:** Reference — every rule here is in force; the ones a check enforces
> name the check. Read this before writing a page.

Documentation for a tool that drives your logged-in accounts and spends your API
quota has one job ordinary documentation does not: **it must not be believed
further than it has earned.** An overstated page is worse than a missing one,
because a missing page sends you to the code and a confident wrong one does not.

Everything below follows from that.

## 1. Every page says what it is

Four markers — **Implemented**, **Partial**, **Planned**, **Reference** — defined
in [the contents](../README.md#status-markers). The banner sits directly under
the H1. `checkBanner` fails a page without one and fails a fifth marker.

The vocabulary is closed on purpose. A marker's whole job is to be comparable
across pages, and a fifth word sorts nowhere against the other four.

The reason it matters here is specific. This project's `providers.yaml` declares
eighteen providers, and a declaration costs three lines. Prose describing a
declared-but-never-run provider reads *identically* to prose describing one that
works — same fields, same selectors, same confident present tense. The banner is
the only thing keeping them apart, which is why a stale banner is the worst
single defect this book can have: it is a claim nobody re-reads.

**Partial is the honest answer far more often than it is comfortable.** Five
pages carry it. When a page is Partial it must say **which half** ships — see
[§5.6](../5-browser-providers/5.6-model-switching.md), whose entire subject is a
mechanism that is complete and configuration that is empty.

## 2. Generated beats hand-kept

Where the code can print a fact, the page carries **the printed output plus the
command that printed it**, not a table someone transcribed.

The worked examples are
[§4.2](../4-api-key-providers/4.2-the-shipped-roster.md) and
[§5.6](../5-browser-providers/5.6-model-switching.md#what-is-configured): both
are fenced blocks of real output, dated, above the command that reprints them.
`providers.yaml` is the truth, and a table that disagrees with it is stale — by
definition and without argument.

This is not hypothetical decay. The old `wiki/pnpm.md` listed `package.json`'s
`files` array without `.env.example`; it was correct when written and had
drifted by the time it was folded into
[§6.4](../6-operating/6.4-pnpm-and-publishing.md#what-ships). Nobody was
careless. A hand-kept copy of a generated fact simply decays.

## 3. One home for the argument, one row for the state

Open work lives in exactly two places, doing different jobs:

| | Owns | Never |
|---|---|---|
| the **chapter** for the subject | why it is unbuilt, what would close it, what was measured | a status the register contradicts |
| [§7](../7-status.md), the **register** | one row: state, one line of evidence, a link to that chapter | a second paragraph |

A row that grows a second paragraph has started drifting from the page it points
at. Move the prose back. `checkRegisterRows` asserts that every row in §7 links
to a page in this book.

The project's own `todo` file is a scratchpad — plans, social-media drafts,
half-finished thoughts. It is not a backlog and this book does not treat it as
one. Where it records a real open item, that item appears as a row in §7 with
`todo` named as its evidence.

## 4. Duplication is not the enemy; undetectable disagreement is

The tempting fix for one fact in two places is to delete a copy. Usually right.
Not always: **two facts at different granularity are not one fact duplicated.**

A page's banner describes the page. A register row describes one item on it.
[§3.1](../3-api/3.1-three-dialects.md) is banner **Partial** while owning four
**Implemented** rows and one working-tree row, and all of those labels are
correct. Collapsing them would lose information, not remove a duplicate.

The same applies across the wiki/docs boundary. This book does not restate
[`docs/api.md`](../../docs/api.md)'s request tables; it links to them and
explains what they cost. Where both must say something — that `/v1/messages`
drops non-text blocks, say — they say it because both audiences need it, and the
code is the tiebreak.

## 5. The vocabulary of not-quite

Four pairs do most of the work, and using them loosely is how a page starts
lying. All four are defined in [§8.2](./8.2-vocabulary.md):

- **`ok` vs verified** — `GET /health` returning `ok: true` means the process
  started, not that any provider works.
- **live-verified vs recon'd** — a selector read off a live DOM is not a
  selector that produced an answer. 2 providers vs 4.
- **declared vs works** — twenty-six model names are declared; two have a
  selector; zero have ever switched a model.
- **implemented vs configured** — the model-switch mechanism is complete and
  does nothing on nine of ten providers.

## 6. Honest absence beats a hopeful claim

A tool that can only fail must not be advertised as working. The documentation
form: write **"never run against the live site"** in the row where you would
rather write nothing.

[§5.5](../5-browser-providers/5.5-what-is-verified.md) is that rule applied at
full cost. It would have been easy to write "ten browser providers supported" —
the README does, and it is not false. This book says two, four and four, with
the commit or the YAML comment behind each, because "supported" and "has ever
produced an answer" are different claims and only one of them is useful.

## 7. Say what was measured, when, and on what

Evidence is specific or it is not evidence. Name the file, the commit, the
timestamp, the machine — `qwen`'s sentinel at
`~/.config/llm-whisperer/profiles/qwen/.logged-in`, reading
`2026-06-21T20:59:59.654Z`, the only one on this machine, checked 2026-08-01.

Dated snapshots are honest in a way undated tables are not: a reader can see how
old a claim is and reprint it. Every generated block in this book carries a date
and its command.

## 8. Keep what was wrong

When something is disproved, the page does not quietly become right. It records
what was believed, what happened, and why the mistake was reasonable.

[§6.2](../6-operating/6.2-startup-and-environment.md#lazy-by-default) keeps the
original eager-warming design next to the `todo` line that killed it, because
"pre-open tabs so the first request is fast" is a sensible idea that will be
proposed again by anyone who hasn't hit the case that breaks it.

## What is checked, and what is not

```bash
node wiki/check.mjs
```

Zero dependencies, runs in under a second. It asserts:

| Check | Fails when |
|---|---|
| `checkStructure` | A page lacks an H1, or lacks a nav footer linking to the contents |
| `checkBanner` | A page has no `> **Status:**` line within 3 lines of its H1, or uses a marker outside the four |
| `checkLinksAndAnchors` | A relative link points at a file that does not exist, or a `#anchor` names a heading that does not exist in the target |
| `checkReachable` | A page under `wiki/` is not linked from [the contents](../README.md) |
| `checkRegisterRows` | A row in [§7](../7-status.md) does not link to a chapter of this book |

Links and headings inside fenced code blocks are stripped before parsing, so
examples in code samples are never mistaken for real links.

Because `wiki/` is in `package.json`'s `files`
([§6.4](../6-operating/6.4-pnpm-and-publishing.md#what-ships)), a broken link
here ships to npm. Run the checker before publishing.

**What no check can verify is whether a Status line is still true.** That is on
whoever changes the code. It is the one place this book depends entirely on
discipline, which is exactly why the banner is one line, at the top, in a
four-word vocabulary — the cheapest possible thing to keep honest.
