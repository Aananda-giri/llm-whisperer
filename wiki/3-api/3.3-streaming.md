# 3.3 Streaming

> **Status:** Partial — OpenAI SSE ships in 0.1.5. Anthropic SSE is implemented
> in the uncommitted working tree only. Both are described here as working code;
> [§7](../7-status.md) tracks the commit status.

Streaming is the one feature that goes all the way down. The route streams
because the provider streams, and the provider streams because
`BaseProvider.chat` is defined as "stream and concatenate"
([§2.3](../2-architecture/2.3-the-provider-contract.md#one-abstract-method)).

Two dialects go out. Two completely different mechanisms come in.

```
   OpenAI SSE  ◀──┐                    ┌──▶ fetch() + parseSSE   (Door A)
                  ├── AsyncGenerator<string> ──┤
Anthropic SSE  ◀──┘                    └──▶ poll the DOM @300ms  (Door B)
```

## Out: two event dialects

**OpenAI** (`src/server.ts:157`) — one JSON object per `data:` line, opening
chunk carries the role, closing chunk carries `finish_reason`, then a literal
sentinel:

```
data: {"id":"chatcmpl-...","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {... "delta":{"content":"Hel"} ...}

data: {... "delta":{},"finish_reason":"stop"}

data: [DONE]
```

**Anthropic** (`src/server.ts:287`) — named events, and a longer required
sequence:

```
event: message_start        → the message envelope, usage all zeroes
event: content_block_start  → index 0, empty text block
event: content_block_delta  → {"type":"text_delta","text":"Hel"}   (repeated)
event: content_block_stop
event: message_delta        → stop_reason: "end_turn"
event: message_stop
```

Both write the same three headers (`text/event-stream`, `no-cache`,
`keep-alive`) and call `res.flushHeaders()` so the client sees the response
start before the first token arrives.

For a plain request, one content block is emitted, always at index 0, always
text. When `tools` are declared on a **browser provider**, the stream carries
more: each parsed `<tool_call>` is flushed as a complete `tool_use` block — on
OpenAI as a `delta.tool_calls` array, on Anthropic as
`content_block_start` + `input_json_delta` + `content_block_stop` with a
`stop_reason: "tool_use"` at the end. The block index advances per block, so
text and tool calls can interleave. The marker is fully buffered before it is
emitted, so a partially-typed `<tool_call` fragment never appears in the wire
(see [§3.1](./3.1-three-dialects.md#what-gets-lost-at-the-edge)).

## Errors mid-stream are not errors

Once headers are flushed the status code is already 200 and cannot be changed.
Both routes handle a mid-stream failure by writing an error into the stream and
closing it:

```ts
} catch (err) {
  res.write(`data: ${JSON.stringify({ error: { message: (err as Error).message } })}\n\n`);
  res.end();
}
```

Consequences worth stating plainly:

- **A streaming request never returns 401.** If a browser session has expired,
  `LoginRequiredError` is thrown from inside the generator, after headers went
  out. The client gets HTTP 200, some or no content, and an error object in an
  unexpected chunk shape. The non-streaming path on the same route returns a
  proper 401.
- The OpenAI error chunk has **no `[DONE]` after it** and no `choices` array, so
  a strict client may hang or throw a parse error rather than surfacing the
  message. The Anthropic path is better behaved here: it emits a real
  `event: error`, which is part of that protocol.
- Partial output already delivered stays delivered. There is no rollback.

## In, Door A: parsing the upstream stream

`ApiLLMProvider` always asks upstream for `stream: true`, even when the caller
wanted a buffered response — the buffering happens locally in `chat()`.

`parseSSE` (`src/providers/api.ts:113`) is a small, correct SSE reader:

```ts
buffer += decoder.decode(chunk, { stream: true });
let sep: number;
while ((sep = buffer.indexOf("\n\n")) !== -1) {
  const event = buffer.slice(0, sep);
  buffer = buffer.slice(sep + 2);
  for (const line of event.split("\n")) {
    // ... if data === "[DONE]" return; else JSON.parse and yield delta
  }
}
```

The two things it gets right that naive versions get wrong: it buffers until a
complete `\n\n`-delimited event is available, so a JSON object split across two
TCP reads still parses; and `decoder.decode(chunk, { stream: true })` keeps
multi-byte UTF-8 characters intact across chunk boundaries. A token containing
an emoji or a CJK character would otherwise arrive as replacement characters.

What it discards: everything except `choices[0].delta.content`. Role deltas,
`finish_reason`, tool calls, and — as noted in
[§3.1](./3.1-three-dialects.md#what-the-response-does-not-contain) — the real
`usage` numbers the upstream sends in its final chunk. A malformed JSON payload
is swallowed by a bare `catch {}` with the comment *"the next event recovers"*,
which is true for keep-alive comments and silently lossy for anything else.

## In, Door B: polling a web page

There is no stream to read from a website, so `streamAnswer`
(`src/providers/base.ts:205`) manufactures one:

```ts
let emitted = "";   // text we've already yielded
while (Date.now() < deadline) {
  const text = (await responses.last().innerText().catch(() => "")).trim();
  if (text !== last) {
    last = text; stableSince = Date.now();
    if (text.startsWith(emitted)) {
      const delta = text.slice(emitted.length);
      if (delta) { yield delta; emitted = text; }
    }
  }
  // ... stop check ...
  await page.waitForTimeout(300);
}
```

Every 300 ms it reads the full text of the last matching element and yields
whatever is new on the end. Three properties follow:

1. **Deltas are chunky.** You get ~3 updates per second of however much the
   model produced in that window, not per-token. It looks like streaming;
   it is a flip-book.
2. **It assumes append-only text.** The `text.startsWith(emitted)` guard is
   there because that assumption fails: when a site re-renders a response —
   closing a markdown code fence, resolving a citation, collapsing a
   "thinking" section — the new text is not a superset of the old, and the
   branch is skipped. `emitted` does not advance, so **the rest of that
   response is dropped from the stream entirely** while the loop keeps
   running until stabilization. The comment calls this "skipped silently",
   which is exactly right and exactly the risk.
3. **`.last()` is doing a lot of work.** Which element is "the answer" is
   whatever `responseSelector` matches last in the DOM. If the selector also
   matches user turns, the last element is your own prompt, and the stream
   yields your question back at you.

When the loop ends is a hard enough problem to get its own page:
[§5.2](../5-browser-providers/5.2-knowing-when-it-stopped.md).
