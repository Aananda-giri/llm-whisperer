# 3.2 Choosing a model

> **Status:** Partial — the `provider/model` string is fully implemented and
> works on all 8 API-key providers. On browser providers the mechanism runs but
> has no configured selectors on 9 of 10; see
> [§5.6](../5-browser-providers/5.6-model-switching.md).

The `model` field in every request is doing two jobs at once:

```
"model": "groq"                          → provider groq, its default model
"model": "groq/llama-3.1-8b-instant"     → provider groq, that model
          ^^^^ ^^^^^^^^^^^^^^^^^^^^^
          which door         which model behind it
```

One line of code, repeated in each route:

```ts
const [providerKey, modelName] = (model as string ?? "").split("/");
```

## Consequences of the slash

`String.split("/")` with no limit and destructuring to two variables produces
some behaviour worth knowing:

- **A model id containing a slash gets truncated.** `openrouter`'s own default
  is `openai/gpt-oss-120b:free` — so `"model": "openrouter/openai/gpt-oss-120b:free"`
  yields `providerKey = "openrouter"`, `modelName = "openai"`, and a request for
  a model called `openai`, which OpenRouter will reject. **There is no way to
  request a slashed OpenRouter model id through this server.** The default (set
  in `providers.yaml`, never split) is reachable; every other OpenRouter model
  with a namespace is not.
- The same trap applies to Cloudflare's `@cf/meta/llama-...` ids and to any
  provider that namespaces. Cloudflare's default works for the same reason —
  it comes from the YAML, not the request.
- `"model": ""` gives `providerKey = ""`, which misses the map and returns a 400
  listing every provider. That is the friendliest error in the codebase.
- `/chat` alone also accepts a separate `provider` field, and prefers it:
  `const target = provider ?? model?.split("/")[0]`.

This is a real limitation with a real fix (split on the *first* slash only,
`model.slice(idx + 1)`), and it is not fixed. It is filed in
[§7](../7-status.md).

## Where the model name goes

**Door A** — `options.model ?? this.api.model` becomes the `model` field of the
upstream request body. Nothing validates it; an unknown id comes back as an
upstream 4xx, wrapped:

```
groq: API request failed (404 Not Found) — {"error":{"message":"model ... does not exist"}}
```

The upstream body is included, truncated to 500 characters. That error message
is the best debugging tool in the project.

**Door B** — `options.model` is passed to `switchModel(page, modelName)`, which
tries to click the site's model picker before typing. It returns silently if the
provider has no `modelPickerTrigger` or no selector for that model name — which
is the case for nine of the ten browser providers. Asking `qwen` for
`qwen/qwen2.5-max` today does not error; it sends your prompt to whatever model
the tab already had selected. [§5.6](../5-browser-providers/5.6-model-switching.md)
has the full census.

## Conversation state is not symmetric

`newChat` and the message history mean different things per door, and this is
the sharpest edge in the API.

**Door A is stateless.** Every request carries the full history; the provider
sends `messages` upstream verbatim. This is standard OpenAI behaviour and needs
no thought.

**Door B is stateful, and reads only your last message.** From
`WebLLMProvider.stream`:

```ts
const lastUser = [...messages].reverse().find((m) => m.role === "user");
const prompt = options.newChat
  ? this.flatten(messages)
  : (lastUser?.content ?? this.flatten(messages));
```

Without `newChat`, the browser provider types **only the most recent user
message** into the box. The conversation history is not sent, because the open
tab already has it — the website is keeping the context, not us. Send a
five-message history and four of them are ignored.

With `newChat: true`, the tab is reset and the whole array is flattened into one
prompt instead:

```
User: ...

Assistant: ...

User: ...
```

Both behaviours are defensible. The trap is that a well-behaved OpenAI client —
which always resends the full history, as it should — gets *correct* results
from Door B by accident, because the tab's own memory happens to line up with
the history the client is tracking. Until it doesn't: two clients sharing one
provider, or a client that edits history, or a server restart, and the tab's
idea of the conversation silently diverges from the caller's.

There is no synchronisation between the two, and no way for a caller to inspect
or reset tab state except `newChat`.

## The listing endpoint tells you less than it looks

`GET /v1/models` returns one entry per **provider key**, not per model:

```jsonc
{"object":"list","data":[{"id":"qwen","object":"model","created":...,"owned_by":"llm-whisperer"}, ...]}
```

Eighteen entries for eighteen providers. The models reachable *behind* each
provider — every Groq model, every OpenRouter model — are not enumerated
anywhere, because llm-whisperer never asks upstream what they are. A UI that
populates a model dropdown from this endpoint shows eighteen options, and the
`provider/model` form has to be typed by hand.
