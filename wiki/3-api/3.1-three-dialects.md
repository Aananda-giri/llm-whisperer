# 3.1 Three dialects, one core

> **Status:** Partial — `/chat`, `/v1/chat/completions`, `/v1/models` and
> `/v1/embeddings` are committed and shipped in 0.1.5. `/v1/messages` is
> implemented and working **in the uncommitted working tree** as of 2026-08-01;
> it is not in the published package. See [§7](../7-status.md).

`src/server.ts` exposes five routes. Four of them are the same request wearing
different clothes.

| Route | Dialect | Shipped in 0.1.5 |
|---|---|---|
| `POST /chat` | native, buffered only | yes |
| `POST /v1/chat/completions` | OpenAI, buffered + SSE | yes |
| `POST /v1/embeddings` | OpenAI | yes |
| `POST /v1/messages` | Anthropic Messages, buffered + SSE | **no — working tree only** |
| `GET /v1/models`, `GET /health` | listings | yes |

Exact request and response shapes for all of them are in
[`docs/api.md`](../../docs/api.md) — this page is about why there are three and
what they cost.

## Why three

Because the point of the project is that existing tools work unmodified
([§1.1](../1-idea/1.1-what-it-is.md)). An OpenAI SDK expects
`/v1/chat/completions` and an object with `choices[0].message.content`. The
Anthropic SDK expects `/v1/messages` and `content[0].text`. Neither will adapt
to a native format, so the server speaks both.

`/chat` is the original endpoint, from before either compatibility layer
existed. It survives because it is the simplest thing to `curl`:

```jsonc
// request
{"provider": "pi", "messages": [{"role":"user","content":"Hello!"}]}
// response
{"provider": "pi", "message": {"role":"assistant","content":"Hi!"}}
```

It is the only route that accepts a separate `provider` field, though it also
accepts `model` and splits it the same way as everything else
(`src/server.ts:89`).

## The common core

Every one of the three chat dialects does exactly this:

```
1. auth gate                    → 401
2. split model on "/"           → providerKey, modelName
3. providers.get(providerKey)   → 400 if unknown
4. messages non-empty?          → 400 if not
5. llm.stream(...) or llm.chat(...)
6. wrap the result in this dialect's JSON
```

Steps 1–5 are identical. Step 6 is the whole difference. The result is about 100
lines of near-duplicate route handler per dialect, and that duplication is
deliberate rather than factored out — each dialect's error envelope, streaming
event sequence and response shape differ in enough small ways that a shared
abstraction would need a parameter for every one of them.

Compare the same failure across the three:

```jsonc
// /chat
{"error": "Unknown provider \"gpt4\". Available: qwen, deepseek, ..."}

// /v1/chat/completions
{"error": {"message": "Unknown provider \"gpt4\". Available: ...",
           "type": "invalid_request_error"}}

// /v1/messages
{"type": "error",
 "error": {"type": "invalid_request_error", "message": "Unknown provider ..."}}
```

Three envelopes for one condition, because that is what each SDK's error parser
expects to find.

## What gets lost at the edge

Providers consume `Message[]` where `content` is a plain string
([§2.3](../2-architecture/2.3-the-provider-contract.md)). Both compatibility
layers accept richer content than that, so both translate it — and what survives
the translation depends on which door the request lands on.

**Anthropic → internal** (`anthropicToMessages`, `src/server.ts`): `blocksToText`
still flattens a `content` value down to text, but for *browser providers*
(Door B) it is called with `keepTools` on, and the tool blocks are routed above
it:

- a `tool_use` block on an assistant turn becomes `assistant.tool_calls`,
- a `tool_result` block on a user turn becomes a `role: "tool"` message.

So tool results reach a browser thread. For API-key providers (Door A)
`keepTools` is off and the old behaviour holds: non-text blocks — images, tool
results, documents — are **silently dropped**, filtered out, and the request
proceeds with whatever text remained.

`anthropicToMessages` also folds the separate `system` field into a leading
`{role: "system"}` message, which is the right translation, and preserves it
only if it is non-empty after trimming.

**OpenAI → internal** (`openaiToMessages`): browser providers are normalized by
flattening a multimodal `content` array to text (fixing the old `[object Object]`
that reached `input.fill(prompt)`) and carrying `tool_calls` / `role: "tool"`
messages through. API-key providers skip the conversion entirely, so an OpenAI
multimodal `content` array reaches Door A untouched and works — the upstream API
gets the array verbatim and does the vision.

The rule that falls out of this: **vision works on the OpenAI endpoint with an
API-key provider, and nowhere else.** `docs/api.md` says so; the code does not
enforce it anywhere.

Tool calling is the other edge that used to be lost. It is now simulated for
browser providers (describe tools in the prompt, parse `<tool_call>` blocks back
into `tool_calls`) and still ignored for API-key providers — see [§3.3](./3.3-streaming.md)
and [§7](../7-status.md).

## What the response does not contain

Every chat response reports zero tokens:

```jsonc
"usage": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0 }
```

This is honest rather than broken. Door B has no token accounting to report —
there is no number to find in a chat website's DOM. Door A *does* receive real
usage from upstream in the final SSE chunk, and llm-whisperer discards it,
because `parseSSE` only ever reads `choices[0].delta.content`
([§3.3](./3.3-streaming.md#in-door-a-parsing-the-upstream-stream)).

So the zeroes are correct for ten providers and a thrown-away fact for the other
eight. Any tool that meters cost against this server sees zero, always. There is
no configuration that changes that.

Likewise absent: `finish_reason` is hard-coded `"stop"` on every successful
OpenAI response, and `stop_reason` is hard-coded `"end_turn"` on every Anthropic
one — except when a tool call was produced, where it becomes `"tool_calls"` /
`"tool_use"`. A response truncated by a browser timeout
([§5.2](../5-browser-providers/5.2-knowing-when-it-stopped.md#the-silent-truncation))
still reports `"stop"` exactly like a complete one.

## GET /health and GET /v1/models

Both just enumerate `providers.keys()`. `/health` is the only route that is
never gated by `WSPR_API_KEY`; `/v1/models` is gated like the rest.

```bash
curl -s localhost:9777/health
# {"ok":true,"providers":["qwen","deepseek",...,"digitalocean"]}
```

`ok: true` means the process is up and the config parsed. It is not a check that
any provider works, that any key is valid, or that any browser session is
alive — see [§8.2](../8-about/8.2-vocabulary.md#ok-vs-verified).
