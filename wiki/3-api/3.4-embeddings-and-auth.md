# 3.4 Embeddings and the auth gate

> **Status:** Implemented — both shipped in 0.1.5 (`d5e39c3`, `0d847ed`).

Two small features that share a page because each is about a boundary: what a
provider can do, and who is allowed to ask.

## Embeddings

`POST /v1/embeddings` is OpenAI-compatible and **API-key providers only**. The
route's third check is the interesting one:

```ts
if (!supportsEmbeddings(llm)) {
  res.status(400).json({ error: {
    message: `Provider "${providerKey}" does not support embeddings (only API-key providers do).`,
    type: "invalid_request_error" } });
  return;
}
```

That is a runtime type guard, not a config flag — see
[§2.3](../2-architecture/2.3-the-provider-contract.md#capabilities-are-structural-not-declared).
A browser provider cannot produce embeddings because a chat website has no
embedding endpoint to drive, so `WebLLMProvider` has no `embed` method, so the
guard returns false. The failure is a clean 400 with a sentence explaining
itself.

```bash
curl http://localhost:9777/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"model":"digitalocean","input":"hello world"}'
```

### The embedModel field exists because chat models aren't embedding models

`ApiProviderConfig` carries an optional `embedModel` alongside `model`, and
`embed()` resolves in this order:

```ts
const embedModel = model ?? this.api.embedModel ?? this.api.model;
```

The final fallback is a chat model, which every embeddings API will reject. The
config comment says so out loud: *"most APIs reject for embeddings — set
`embedModel` instead."*

Only two of the eight API providers set one:

| Provider | `embedModel` |
|---|---|
| `openai` | `text-embedding-3-small` |
| `digitalocean` | `gte-large-en-v1.5` (also available: `bge-m3`) |

So `{"model":"groq"}` on this endpoint reaches Groq asking
`llama-3.3-70b-versatile` for embeddings and gets an upstream error. The other
six providers work on this endpoint **only if you name a model explicitly**:
`{"model":"gemini/text-embedding-004"}`. That is a real gap, filed in
[§7](../7-status.md), and the fix is six lines of YAML.

The upstream response is passed through unmodified except for one field —
`model` is overwritten with whatever string the caller sent, so the response
echoes `"digitalocean/bge-m3"` rather than upstream's bare id.

## The auth gate

`WSPR_API_KEY` is the only authentication in the project.

```ts
const apiKey = process.env.WSPR_API_KEY ?? "";
// ...
if (!apiKey) return next();   // unset ⇒ the gate does not exist
```

Unset or empty means **every route is open**. That is the default, and it is the
right default for something bound to localhost that a user starts to talk to
themselves. Set it and every route except `GET /health` requires the key, in
either of two headers:

```
Authorization: Bearer <key>
x-api-key: <key>
```

Two headers because two SDKs: the OpenAI client sends `Authorization: Bearer`,
the Anthropic client sends `x-api-key`. `extractKey` checks Bearer first, then
`x-api-key`, and returns `undefined` if neither is present
(`src/server.ts:50`).

There are two gate middlewares, differing only in the error envelope —
`requireApiKey` for `/v1/*` and `requireApiKeySimple` for `/chat` — matching the
per-dialect error shapes from
[§3.1](./3.1-three-dialects.md#the-common-core).

### What this is and is not

It is a shared secret compared with `!==`. It is enough to stop a casual scan of
your LAN from spending your Groq quota.

It is not: rate limiting, per-caller identity, an audit log, a constant-time
comparison, or anything that survives being sent over plain HTTP — which is the
only thing this server speaks. There is no TLS, no `--bind` flag, and
`app.listen(port)` with no host argument binds **all interfaces**, not just
loopback.

That last point is worth being blunt about, because the README frames
`WSPR_API_KEY` as being for when you "expose it on a network": `wspr serve` is
*already* reachable from your network on port 9777, with or without the key set.
The key is not what exposes it; it is the only thing that protects it once
exposed. If you are on an untrusted network and you have not set
`WSPR_API_KEY`, anyone who can reach the port can spend your API quota and read
your browser sessions' conversations.

Binding to `127.0.0.1` by default is filed as unbuilt in [§7](../7-status.md).
