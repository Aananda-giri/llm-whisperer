# 1.2 The two doors

> **Status:** Implemented — both doors exist and run. Their *reliability*
> differs enormously, which is the point of this page.

llm-whisperer can reach a model two ways, and almost every design decision in
the codebase is downstream of supporting both at once.

| | **Door A — API key** | **Door B — browser** |
|---|---|---|
| How | HTTPS to an OpenAI-compatible endpoint | Playwright drives the real chat website |
| Needs | An API key in an env var | A one-time hand login, saved as a browser profile |
| Providers shipped | 8 | 10 |
| Class | `ApiLLMProvider` (`src/providers/api.ts`) | `WebLLMProvider` (`src/providers/base.ts`) |
| Breaks when | Your quota runs out | The site changes its HTML |
| Streaming | Real SSE, forwarded from upstream | Polling the DOM every 300 ms |
| Embeddings | Yes | No |
| Conversation state | Stateless — you resend history | Lives in the open tab |
| Terms of service | Fine — it's the official API | Usually prohibited. [§1.3](./1.3-terms-of-service.md) |

Both are chosen the same way, by the caller, with one word:

```jsonc
{"model": "groq"}    // door A — hits api.groq.com
{"model": "qwen"}    // door B — types into chat.qwen.ai in a real browser
```

Nothing in the request says which door it is. That is deliberate: the caller is
an OpenAI SDK that has never heard of llm-whisperer, so the two doors must be
indistinguishable from outside. [§2.3](../2-architecture/2.3-the-provider-contract.md)
is how that indistinguishability is actually enforced — a single interface with
one abstract method.

## Which door a provider uses

There is exactly one switch, and it is in the YAML:

```ts
// src/providers/factory.ts
if (cfg.api) {
  providers.set(name, new ApiLLMProvider(name, cfg));
  continue;
}
const Cls = OVERRIDES[name] ?? WebLLMProvider;
providers.set(name, new Cls(name, cfg, pool));
```

A provider with an `api:` block is Door A. A provider without one is Door B.
That is the whole dispatch — `src/providers/factory.ts:24`. Adding a ninth
API-key provider is a YAML edit and no TypeScript at all
([§4.1](../4-api-key-providers/4.1-one-class-many-services.md)).

`OVERRIDES` is an escape hatch for browser providers that need real code beyond
selectors. **It has never been used.** The map is empty, with a commented-out
example inside it. Ten browser providers have so far been describable purely as
configuration, which is the strongest evidence the design has for itself.

## Why Door B exists at all

Door A is better in every technical respect. Door B exists because free tiers
have limits and free *chat websites* mostly don't — Pi, Qwen, ChatGPT, Claude,
DeepSeek and the rest will talk to you all day in a browser without a credit
card. If Door A is "pool the free API tiers", Door B is "and the free web UIs
too".

It is also the older half of the project. The name is Door B's name: you
*whisper* to a chat UI that thinks you're a person.

## Why you should mostly use Door A

The book's honest recommendation, and the README's:

- Door A works. Door B works **on two of its ten providers** as of 2026-08-01,
  and the other eight are best-effort selectors nobody has run end to end. The
  evidence for each is in [§5.5](../5-browser-providers/5.5-what-is-verified.md).
- Door A is stable. Door B breaks whenever a frontend team ships a redesign,
  and you find out through a timeout screenshot in `/tmp`
  ([§6.3](../6-operating/6.3-when-a-provider-breaks.md)).
- Door A is permitted. Door B is, for nearly every provider, a terms-of-service
  violation you are choosing to commit. That deserves its own page, next.
