# 5.6 Model switching

> **Status:** Partial — the mechanism is fully implemented and the API accepts
> it. The **configuration it needs is empty on 9 of 10 browser providers**, so on
> those nine the feature is a silent no-op. On API-key providers, model
> switching works completely ([§3.2](../3-api/3.2-choosing-a-model.md)).

This page is the clearest example in the project of the difference between
*built* and *works*, so it is worth reading even if you never switch a model.

## What was built

Commit `77afb79`, *"Add model selector: switch models within a provider via
API"*. Three pieces, all real:

**1. The API accepts it.** Every route splits `provider/model` and passes
`modelName` through as `ChatOptions.model`
([§3.2](../3-api/3.2-choosing-a-model.md)).

**2. The config has a place for it.**

```ts
/** Click this to open the model picker dropdown. */
modelPickerTrigger?: string;
/** Map of model name → selector to click inside the picker. */
models?: Record<string, string>;
```

**3. The driver clicks through it.**

```ts
protected async switchModel(page: Page, modelName: string): Promise<void> {
  const { modelPickerTrigger, models } = this.config;
  const optionSelector = models?.[modelName];
  if (!modelPickerTrigger || !optionSelector) return;
  await page.locator(modelPickerTrigger).first().click().catch(() => {});
  await page.waitForTimeout(400);
  await page.locator(optionSelector).first().click().catch(() => {});
  await page.waitForTimeout(400);
}
```

Open the picker, wait 400 ms, click the option, wait 400 ms. That is a correct
description of how you switch models on every one of these sites.

**Twenty-six model names are declared across the ten providers. Two of them have
a selector.** Both belong to `minimax` — which is itself only recon'd, never run
([§5.5](./5.5-what-is-verified.md)). So the number of browser model-switches
that have ever demonstrably happened is zero.

Every other row lists models with empty-string selectors:

```yaml
  qwen:
    modelPickerTrigger: ""
    models:
      "qwen3-235b":    ""
      "qwen3-30b":     ""
      "qwen2.5-max":   ""
```

## Why the failure is silent

```ts
if (!modelPickerTrigger || !optionSelector) return;
```

Empty string is falsy, so `switchModel` returns immediately, and `stream()`
carries on to submit the prompt. There is no throw, no log line, no field in the
response.

```bash
curl localhost:9777/v1/chat/completions \
  -d '{"model":"qwen/qwen2.5-max","messages":[{"role":"user","content":"hi"}]}'
```

That request succeeds. It returns an answer. The answer comes from whatever
model the Qwen tab happened to have selected — probably the site default,
possibly something a previous request left behind. The response echoes
`"model": "qwen/qwen2.5-max"` back at you, because the route echoes the request
string without consulting anything.

**The response asserts a model that was never selected.** That is the whole
defect, and it is worse than an error would be, because a caller logging the
response has a record saying it used a model it did not use.

The two `.catch(() => {})` clauses inside `switchModel` extend the same
silence to configured providers: if `minimax`'s picker selector is stale, the
clicks fail, the prompt is sent anyway, and the response still claims the
requested model.

## Why it is like this

The mechanism was written before the selectors — sensible order, since without
the mechanism there is nowhere to put them. The model *names* were then filled
in from each site's marketing copy, which costs nothing and requires no browser,
while the *selectors* need a logged-in session, an open picker, and devtools.

Nine providers' pickers were never opened. The `todo` file has `- [ ] model
selector` still unchecked, which reads as a contradiction of commit `77afb79`
and is in fact the more accurate of the two statements.

## Closing it

Per provider, roughly twenty minutes:

1. `HEADLESS=false wspr serve`, send one request to open the tab.
2. Click the model picker in the visible window; copy a selector for the
   trigger from devtools.
3. With the dropdown open, copy a selector for each option.
4. Fill in `modelPickerTrigger` and the `models` map; restart; send
   `provider/model` and **watch the picker change in the window**. That last
   step is what turns this from configured into verified.

Two improvements would help more than the selectors:

- **Fail loudly.** If `options.model` is set and no selector matches, throw
  rather than return. A 400 saying *"provider `qwen` has no configured selector
  for model `qwen2.5-max`"* is strictly better than a confident wrong answer.
- **Delete the empty maps.** Twenty-four model names with no selectors are worse
  than absent: they look like a capability list. An honest `models: {}` says
  what is true.

Both are filed in [§7](../7-status.md).
