# 5.3 Sessions and login

> **Status:** Implemented — `src/browser.ts` and the `login` command in
> `src/cli.ts`, shipped. Named browser profiles added 2026-08. Autonomous login
> via the credential vault added 2026-09.

Browser providers need you logged in. Chromium writes its cookies to a profile
directory; every later request reuses that profile. Historically you logged in
by hand once per provider, and the tool never saw a password — it had no way to
fill a login form and no place to keep a secret.

Both of those are now false. The credential vault (`src/credentials/vault.ts`)
stores an encrypted password per provider×profile, and the login driver
(`src/credentials/login.ts`) submits it on your behalf when a session lapses.
That is a deliberate trade: the convenience costs you a stored password, and
§1.3 states plainly what it means for the project's terms-of-service position.

## One browser per profile

```ts
private profileContext(profile: string, headless: boolean): Promise<BrowserContext> {
  const userDataDir = resolve(join(
    this.profilesDir,
    profile === DEFAULT_BROWSER_PROFILE ? "browser" : "browser-profiles",
    ...(profile === DEFAULT_BROWSER_PROFILE ? [] : [profile]),
  ));
  mkdirSync(userDataDir, { recursive: true });
  return stealthChromium.launchPersistentContext(userDataDir, { ... });
}
```

The default profile keeps the original path, `profilesDir/browser` — one
directory, singular, shared by every provider that does not name a profile.
Upgrading does not lose existing logins. Named profiles get their own
directory under `profilesDir/browser-profiles/<profile>/`, and each is a
separate Chromium process with its own cookies and local storage.

The original design had exactly one profile for all ten providers. The comment
in `src/browser.ts` explains why sharing one profile is safe:

> Chrome partitions cookies by origin, so qwen.ai, deepseek.com, etc. never
> bleed into each other.

Which is correct, and buys a great deal: one Chromium process instead of ten,
one launch cost, one memory footprint. It also means a single Google login can
satisfy several providers' OAuth at once.

What sharing cannot do is hold *two accounts on the same site* — same origin,
same cookie jar. Named profiles are for that: `email1` logged in to DeepSeek,
ChatGPT, and Claude; `email2` logged in to a different set. A profile is chosen
by the first of: the request's `profile` field, the provider's `profile:` field
in `providers.yaml`, `WSPR_BROWSER_PROFILE`, and finally `"default"`. The
`AppConfig` env default is materialized into every browser provider at config
load, so the chain resolves in one place (`loadConfig` in `src/config.ts`).

`BrowserManager.contexts` caches a `Promise<BrowserContext>` per profile, so
concurrent first requests for the same profile all await the same launch rather
than racing to start two browsers.

## The lock

Chromium locks its user-data directory to one process, *per profile*.
`wspr serve` holds the `default` profile's lock as soon as any default-profile
provider is used. So:

```
wspr login qwen            # fails if `wspr serve` is using "default"
wspr login qwen email1     # fine — "email1" has its own directory
```

The CLI catches it and says so in the one place it matters
(`src/cli.ts`):

```
Could not open the browser. If "wspr serve" is running, stop it first —
Chrome locks each profile to one process at a time.
```

**Stop the server (or pick a different profile), log in, start the server.**
This is the most common operational surprise in the project, and it is a direct
consequence of the persistent-profile design. The named-profile escape hatch is
new: you can log in to a second account while the server is busy with the
first, so long as they are different profiles.

## The login flow

`wspr login <name> [profile]` (`src/cli.ts`) is deliberately dumb, and now
optionally not so dumb:

1. Resolve the profile: the CLI argument, else the provider's configured
   `profile` (which already includes the `WSPR_BROWSER_PROFILE` default).
2. Launch the browser **non-headless**, always —
   `browser.context(profile, { headless: false })`, ignoring `HEADLESS`.
3. `page.goto(provider.url)`.
4. **Auto-login attempt** — if a credential and `login:` block exist for this
   provider×profile, fill and submit the form. If it succeeds, skip to step 6.
5. Otherwise print *"Log in, get to the chat screen, then press Enter to save
   the session."* and block on a single keypress: `process.stdin.once("data", ...)`.
6. Close the browser, which flushes the profile to disk.
7. **Verify** with `isLoggedIn`; only if the page really shows a chat surface,
   write the sentinel — `profilesDir/<name>/.logged-in` for the default profile,
   `profilesDir/<name>/<profile>.logged-in` for named ones — else exit non-zero.
   See [§8.2](../8-about/8.2-vocabulary.md#ok-vs-verified).

The sentinel is also the only per-provider thing in `profilesDir`. The actual
session — cookies, local storage, the thing that matters — lives in the profile
directory. Deleting `profilesDir/qwen/.logged-in` does not log you out; deleting
`profilesDir/browser/` logs you out of every default-profile session, and
deleting `profilesDir/browser-profiles/email1/` logs you out of that account.

## The credential vault and auto-login

`wspr login <name>` becomes hands-free when a declarative `login:` block is
configured for the provider and a credential is stored for that provider×profile:

```bash
wspr creds set qwen            # prompt email + password, hidden
wspr login qwen                # fills the form, skips the Enter prompt if it works
wspr login --all               # every provider with a password credential, in turn
```

The driver is `attemptLogin` in `src/credentials/login.ts`. It clicks the
optional `trigger`, fills `emailSelector`, optionally clicks `continueSelector`,
fills `passwordSelector`, clicks `submitSelector`, waits for `successSelector`
(defaulting to the provider's `inputSelector`), then confirms with the *same*
`isLoggedIn`. On failure it screenshots to `/tmp` and returns a reason rather
than throwing, so the caller falls back to the manual flow.

Rules that hold regardless of the provider:

- **One failed attempt, never retried.** A repeated failure locks accounts, so
  a credential that fails is marked and not tried again until it changes —
  `updatedAt` is part of the key, so `wspr creds set` clears the mark. A
  *successful* login is not marked: a long-running `wspr serve` has to be able
  to recover the same session the next time it lapses. The dashboard's Login
  button goes through the same guard (`WebLLMProvider.autoLogin`), so clicking
  it repeatedly cannot replay a wrong password.
- **`method: "manual"`** (Claude's emailed magic link, any Google OAuth) fills
  only the email, then hands the window to you — a real improvement over a blank
  login screen, but not full autonomy.
- **Auto-login is on** by default when a vault is unlocked (`WSPR_VAULT_KEY`),
  and gated off by `WSPR_AUTO_LOGIN=false`.
- If auto-login can't recover the session, requests still fail with
  `LoginRequiredError` exactly as before. Auto-login never makes a working
  session worse.

The vault lives at `$PROFILES_DIR/credentials.enc` — AES-256-GCM, scrypt KDF,
mode `0600`, never committed. Its redacted view (`listRedacted`) omits passwords
and is the only thing the `/ui` dashboard may see; reading a password back is
`wspr creds show` on the CLI.

### What the sentinel is used for

Exactly one thing: deciding which tabs to pre-open when `WSPR_WARM=true`
(`src/cli.ts`). Warming is limited to the default profile — named profiles
launch lazily on first use, so warming N profiles would mean N browser
processes at boot.

```ts
if (cfg.profile !== DEFAULT_BROWSER_PROFILE) return false; // named: lazy
if (!cfg.requiresLogin) return true;
return existsSync(sentinelPath(config.profilesDir, name, DEFAULT_BROWSER_PROFILE));
```

With warming off — the default ([§6.2](../6-operating/6.2-startup-and-environment.md#lazy-by-default)) —
the sentinel is read by nothing at all. Whether you are actually logged in is
determined at request time by `ensureLoggedIn`
([§5.1](./5.1-the-generic-driver.md#are-we-logged-in)), which looks at the page,
not at the file.

## Which browser

```ts
browserChannel: resolveBrowserChannel(),
```

Unset, or `chromium`, means Playwright's bundled Chromium — zero extra install
beyond `npx playwright install chromium`. `WSPR_BROWSER_CHANNEL=chrome` launches
your locally-installed Google Chrome instead. The legacy `BROWSER` variable is
honoured only when it names a known Playwright channel; desktop launcher
commands exported as `BROWSER` (e.g. `omarchy-launch-browser`) are ignored.

That option exists for one specific reason, recorded in the `AppConfig` comment:
Google's sign-in flow blocks bundled Chromium with *"this browser may not be
secure"*, which makes Google OAuth — and therefore Qwen login — impossible
without it. If a provider's login is Google OAuth, `WSPR_BROWSER_CHANNEL=chrome`
is not a preference, it is the requirement.

## CDP mode

The third option is to not launch a browser at all and attach to one you started:

```bash
pnpm run chrome   # google-chrome --remote-debugging-port=9222 --user-data-dir=...
CDP_URL=http://localhost:9222 wspr serve
```

```ts
const browser = await playwrightChromium.connectOverCDP(this.cdpUrl!);
return browser.contexts()[0] ?? browser.newContext({ viewport: { width: 1280, height: 900 } });
```

It reuses the running browser's **existing default context**, so you are already
logged in to everything that browser is logged in to — no `wspr login` at all,
no profile lock, and no stealth plugin either (it is only applied to launched
contexts). `.env.example` calls this the recommended mode.

The catch is that it takes over `contexts()[0]` — your ordinary browsing
context. Tabs open and navigate in the window you are using. There is nothing
isolating your session from the automation, which is the point and also the
risk.

Named profiles are rejected in CDP mode: the attached browser *is* the profile.
To switch accounts, start a second Chrome with a different `--user-data-dir`
and point a second `wspr serve` at it.
