# 5.4 The session pool

> **Status:** Implemented — `src/session-pool.ts`, shipped. Profile-keyed
> pools added 2026-08.

Two requests to `qwen` at the same time cannot share one browser tab: the second
`fill()` would overwrite the first prompt mid-flight. The pool exists to stop
that, and to cap how many tabs one provider can open.

```ts
export class SessionPool {
  private idle    = new Map<string, Page[]>();
  private active  = new Map<string, number>();
  private waiters = new Map<string, ((page: Page) => void)[]>();

  constructor(private browser: BrowserManager, private maxPerProvider = 2) {}

  private key(provider: string, profile: string): string {
    return `${profile}\u0000${provider}`;
  }
}
```

Three maps keyed by `profile\u0000provider` (a `\u0000` separator because profile
names may legally contain no NUL): pages available for reuse, a count of pages
in existence, and a queue of requests waiting for one. The profile is part of
the key because a tab belongs to a browser *context*, and each profile is its
own context — a `qwen` page in `email1` is useless to a request for `qwen` in
`email2`.

## Acquire

```ts
async acquire(provider: string, profile: string): Promise<Page> {
  const key = this.key(provider, profile);
  const idle = this.idle.get(key) ?? [];
  // ...pop a live page, or newPage(profile), or park a waiter...
}
```

In order: reuse an idle page, decrementing `active` for any that the user closed
by hand; otherwise create one if under the cap; otherwise park an unresolved
promise in the waiters queue. `release` hands the page directly to the first
waiter rather than returning it to the idle list, so a queued request resumes
immediately.

`maxPerProvider = 2` is a constructor default with no override — `new
SessionPool(browser)` in `src/cli.ts:51` is the only construction in the
codebase. Two concurrent conversations per provider, not configurable by
environment variable or flag. Filed in [§7](../7-status.md).

Reusing an idle page is what makes conversation continuity work: the tab still
holds the previous exchange, and `ensureOnPage` won't navigate away from it
([§5.1](./5.1-the-generic-driver.md#navigate-only-if-youre-not-already-there)).

## The profile argument that is used

```ts
private async newPage(profile: string): Promise<Page> {
  try {
    const ctx = await this.browser.context(profile);
    return await ctx.newPage();
  } catch {
    await this.browser.close();
    return (await this.browser.context(profile)).newPage();
  }
}
```

Originally the argument was underscored (`_provider`): a new page was a new page,
identical regardless of which provider asked. With named profiles the argument
earns its keep — the page must come from the *profile's* context, and pages
become provider-specific only when `ensureOnPage` navigates them.

The consequence is that **the pool's bookkeeping is a fiction the pool itself
maintains.** A page created for `qwen` in `email1` and returned to
`idle["email1\0qwen"]` is only "qwen's tab" because the map says so — nothing
in Playwright ties them. If that bookkeeping ever leaked a page from one
bucket to another, the result would be a tab on the wrong site, and
`ensureOnPage` would quietly navigate it and lose the conversation. It doesn't
leak, but the invariant lives entirely in this one file.

The `catch` is a crude but effective recovery: if the context is dead — the
user closed the window, Chromium crashed — close everything and relaunch once.
`BrowserManager.close()` now closes **every** profile's context (it iterates
`this.contexts`), so one crashed profile takes the others down with it; the
next `.context()` per profile performs a fresh launch. One retry, no backoff;
a second failure propagates.

## What it doesn't do

- **No idle timeout.** A page sits in the idle map forever. A tab used once at
  startup is still open, still rendering, still consuming memory a week later.
  Nothing reaps it.
- **No global cap.** Ten browser providers × 2 = up to 20 tabs per profile,
  and the pool only counts per provider×profile.
- **No fairness or timeout in the queue.** Waiters are FIFO and wait
  indefinitely. If a request wedges — a hung page, a provider that never
  stabilises before its 90-second deadline — everything queued behind it waits
  that long. There is no way to cancel a waiter, so a client that disconnects
  still leaves its promise in the queue, and the page eventually handed to it is
  released back only when the abandoned generator's `finally` runs.
- **No health check on reuse.** `isClosed()` is the only test. A page that
  navigated to an error page, hit a Cloudflare challenge, or logged out is
  handed back out as good; the failure surfaces later in `ensureLoggedIn` or as
  a timeout.

For one person driving a handful of chats, none of this matters. All of it would
matter for a shared deployment, which [§1.1](../1-idea/1.1-what-it-is.md#what-it-is-not)
says the project is not.

## Shutdown

```ts
const shutdown = async () => {
  console.log("\nShutting down...");
  server.close();
  await browser.close();
  process.exit(0);
};
process.on("SIGINT", shutdown);
process.on("SIGTERM", shutdown);
```

`browser.close()` closes every profile's context, which closes every page and
flushes each profile to disk. The pool is never told, and doesn't need to be —
the process is ending. `server.close()` is not awaited, so in-flight HTTP
responses are cut off rather than drained.
