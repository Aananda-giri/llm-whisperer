# 5.2 Knowing when it stopped talking

> **Status:** Implemented — `streamAnswer` and `isStreaming`, shipped. This page
> describes working code and the failure modes it cannot avoid.

An HTTP API tells you when a response is over: the stream sends `[DONE]`, or the
connection closes. A web page tells you nothing. It just… stops changing.

This is the hardest problem in the codebase, and the answer is two heuristics
stacked on a timeout.

## The three exits

`streamAnswer` (`src/providers/base.ts:205`) can end three ways:

| Exit | Condition | What the caller gets |
|---|---|---|
| **Stabilized** | Not streaming, *and* text unchanged for `stabilizeMs` | The full answer |
| **Deadline, waiting** | `timeoutMs` elapsed before a new node appeared | A thrown error + a screenshot |
| **Deadline, mid-answer** | `timeoutMs` elapsed while text was still growing | A truncated answer, **no error** |

Those three are very different events and only one of them is reported.

## Heuristic 1: the stop button

```ts
protected async isStreaming(page: Page): Promise<boolean> {
  if (!this.config.stopSelector) return false;
  return page.locator(this.config.stopSelector).first().isVisible().catch(() => false);
}
```

Nearly every chat UI swaps its send button for a "stop generating" control while
the model is producing. Its visibility is the most direct signal available that
generation is in progress.

Note the default: **no `stopSelector` means "never streaming."** So a provider
without one falls entirely through to heuristic 2. `pi` is configured exactly
this way, and the YAML comment says why — *"Pi has no reliable streaming
indicator, so we rely on text stabilization."*

## Heuristic 2: the text stopped changing

```ts
if (text !== last) { last = text; stableSince = Date.now(); /* ...yield... */ }

const stillStreaming = await this.isStreaming(page);
if (!stillStreaming && last && Date.now() - stableSince >= stabilizeMs) return;
await page.waitForTimeout(300);
```

Both conditions must hold: no stop button visible, **and** the text has not
changed for `stabilizeMs` (2000 ms for eight providers, 1500 ms for `pi`).
`last` must also be non-empty, so an empty response element can never satisfy
the exit.

The `stabilizeMs` value is a bet on a number nobody measured. Too low and a
model that pauses mid-answer — thinking, calling a tool, rendering a diagram —
looks finished, and you get half an answer marked complete. Too high and every
single request pays that delay at the end, because the loop cannot know the
answer is done until the timer expires. Two seconds on every request is the
price of not having a real completion signal.

## The silent truncation

The loop's last line is a comment, and it is the most important comment in the
file:

```ts
  while (Date.now() < deadline) { /* ... */ }
  // Generator returns without throwing — caller has already received partial output.
}
```

If the deadline passes while the model is still producing, the generator simply
returns. No error, no flag, no warning. The route wraps up whatever it has:

- a non-streaming caller gets HTTP 200, a truncated answer, and
  `finish_reason: "stop"`
- a streaming caller gets a clean `[DONE]`

**A response cut off at 90 seconds is indistinguishable from a complete one.**
There is no field in any of the three dialects that would carry the difference,
because the response shapes are hard-coded
([§3.1](../3-api/3.1-three-dialects.md#what-the-response-does-not-contain)).
Long answers from slow providers are the case where this bites, and it is filed
in [§7](../7-status.md).

The other deadline — no new response node ever appeared — *does* throw, and does
it well:

```ts
await page.screenshot({ path: `/tmp/${this.name}-timeout.png` }).catch(() => {});
throw new Error(
  `${this.name}: timed out waiting for a response to start` +
    ` (url=${page.url()}, screenshot=/tmp/${this.name}-timeout.png)`,
);
```

A screenshot and the current URL, named in the error message. When a site
redesign breaks a selector this is what you see first, and it usually contains
the answer — a consent banner, a Cloudflare challenge, a logged-out home page.
[§6.3](../6-operating/6.3-when-a-provider-breaks.md) is the repair loop that
starts here.

The two deadlines share one `timeoutMs`, so a provider set to 90 s can spend the
whole budget waiting for a node that never comes, and a provider that starts
promptly gets the same 90 s to finish. There is no separate "time to first
token" setting.

## Why polling at all

Playwright can wait on DOM mutations, and a `MutationObserver` would give exact
deltas with no polling interval. The driver polls `innerText()` every 300 ms
instead.

The trade is robustness for fidelity. `innerText()` returns rendered text
regardless of how the site produces it — React re-renders, streaming
`textContent` appends, virtual DOM swaps, shadow roots — and needs to know
nothing about the app's internals. A mutation-based reader needs to know which
node to observe and how that site mutates it, which is exactly the
provider-specific knowledge the config-driven design exists to avoid
([§2.2](../2-architecture/2.2-configuration-is-the-product.md)).

The cost is [§3.3](../3-api/3.3-streaming.md#in-door-b-polling-a-web-page): ~3
updates per second instead of per-token, and the append-only assumption that
silently drops the tail of a re-rendered response.
