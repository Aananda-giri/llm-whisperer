# 5.5 What is actually verified

> **Status:** Partial — 2 of 10 browser providers have been driven end to end.
> The other 8 ship configuration that has never produced an answer. This page is
> the evidence for each.

`providers.yaml` declares ten browser providers, and the server will happily
accept a request for any of them. Declaring a provider costs three lines of
YAML. Making one work costs an afternoon with devtools open.

The gap between those two numbers is this page.

## The three levels

| Level | Means | Count |
|---|---|---|
| **Live-verified** | A real request produced a real answer from the real site. | 2 |
| **Recon'd** | Selectors were read off the live DOM by a human. No request was ever run. | 4 |
| **Template** | Plausible selectors, written from the pattern the other providers follow. | 4 |

Definitions are in [§8.2](../8-about/8.2-vocabulary.md#live-verified-vs-recond).
The distinction is not pedantry: a recon'd provider has a correct
`inputSelector` and an unknown `responseSelector`, and an unknown
`responseSelector` is the failure that returns your own prompt back to you
([§5.1](./5.1-the-generic-driver.md#counting-before-and-after)).

All four recon'd providers name the same missing piece: the **response**
selector. Reading an input box off a page is easy — it's the focused element.
Knowing which container will hold an answer that hasn't been generated yet
requires generating one.

## The strongest single piece of evidence

Login sessions leave a sentinel file
([§5.3](./5.3-sessions-and-login.md#the-login-flow)). Here is every one that
exists on this machine, across both the current default directory and the older
repo-local one:

```console
$ find ~/.config/llm-whisperer/profiles -maxdepth 2 -name .logged-in
/home/anon-labs/.config/llm-whisperer/profiles/qwen/.logged-in

$ cat ~/.config/llm-whisperer/profiles/qwen/.logged-in
2026-06-21T20:59:59.654Z

$ find ./profiles -maxdepth 2 -name .logged-in      # older PROFILES_DIR=./profiles
./profiles/qwen/.logged-in                          # 2026-06-20T18:19:58.032Z
```
<sub>Run 2026-08-01.</sub>

Nine of the ten browser providers require login. **One session has ever been
saved, for `qwen`, and `pi` is the only other provider that could have run
without one.** That is the same two providers as the table above, arrived at
from a completely different direction.

Four stale profile directories exist for `chatgpt`, `claude`, `glm` and
`deepseek` — created by `wspr login` runs on 2026-06-21 that were started and
never completed, since no sentinel was written. Nobody has attempted `kimi`,
`minimax`, `grok` or `ernie` at all.

## What this means for you

- **`pi` is the honest first thing to try.** No login, live-verified, and the
  quickest possible check that the machinery works at all
  ([§6.1](../6-operating/6.1-install-and-first-run.md)).
- **`qwen` is the verified logged-in path**, and its login is Google OAuth, so
  it needs `WSPR_BROWSER_CHANNEL=chrome`
  ([§5.3](./5.3-sessions-and-login.md#which-browser)).
- **The other eight are a starting point, not a feature.** Expect to open
  devtools. [§6.3](../6-operating/6.3-when-a-provider-breaks.md) is the loop.

Nothing in the code marks the difference. A request to `claude` and a request to
`pi` take the same path through the same class, and the server has no idea one
of them has never worked. `GET /health` lists all eighteen providers regardless
([§3.1](../3-api/3.1-three-dialects.md#get-health-and-get-v1models)).

## Why the book says so instead of quietly shipping ten

A tool that can only fail should not be advertised as working, and the
documentation form of that rule is to write **"never run against the live
site"** in the row where it would be more comfortable to write nothing
([§8.1](../8-about/8.1-how-this-book-is-written.md)).

The counts here will change, and when they do the right edit is to move a row
up a level *and record what was run* — not to quietly delete the column.
