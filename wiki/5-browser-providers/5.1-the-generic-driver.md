# 5.1 The generic driver

> **Status:** Implemented — `WebLLMProvider` in `src/providers/base.ts`, shipped.
> That the driver *runs* is implemented; whether it works against a given site
> is [§5.5](./5.5-what-is-verified.md).

One class drives ten different chat websites. Its entire public surface is the
`stream()` inherited from the contract
([§2.3](../2-architecture/2.3-the-provider-contract.md)), and the body is
readable in one screen:

```ts
async *stream(messages: Message[], options: ChatOptions = {}): AsyncGenerator<string> {
  const profile = validateBrowserProfile(
    options.profile ?? this.config.profile ?? DEFAULT_BROWSER_PROFILE,
  );
  const page = await this.pool.acquire(this.name, profile);
  try {
    await this.ensureOnPage(page);
    await this.ensureLoggedIn(page);

    if (options.newChat) await this.newConversation(page);
    if (options.model)   await this.switchModel(page, options.model);

    const lastUser = [...messages].reverse().find((m) => m.role === "user");
    const prompt = options.newChat ? this.flatten(messages) : (lastUser?.content ?? this.flatten(messages));

    const before = await this.countResponses(page);
    await this.submitPrompt(page, prompt);
    yield* this.streamAnswer(page, before);
  } finally {
    this.pool.release(this.name, profile, page);
  }
}
```

Seven steps, each a `protected` method a subclass could override, and none of
them yet overridden by anything
([§2.3](../2-architecture/2.3-the-provider-contract.md#the-escape-hatch-nobody-needed)).
The `finally` matters: the page returns to the pool on every path, including a
thrown `LoginRequiredError` and including a caller that abandons the generator
early.

## Navigate only if you're not already there

```ts
if (!page.url().startsWith(new URL(this.config.url).origin)) {
  await page.goto(this.config.url, { waitUntil: "domcontentloaded" });
}
```

The origin check, not a URL equality check, is what makes conversation
continuity work. After a first request the tab sits at
`https://chat.qwen.ai/c/abc123` — a different URL, the same origin — so the
second request does not navigate, and the open conversation with all its context
is still there. Reloading would lose it.

`waitUntil: "domcontentloaded"` rather than `networkidle` is a deliberate
cheapness: modern chat apps never go network-idle (websockets, telemetry,
polling), so waiting for it would hang. The cost is that the DOM may not be
interactive yet, which is absorbed by the `waitFor({ state: "visible" })` in
`submitPrompt`.

## Are we logged in?

```ts
protected async ensureLoggedIn(page: Page): Promise<void> {
  if (!this.config.requiresLogin) return;

  if (this.config.loggedOutSelector) {
    const out = await page.locator(this.config.loggedOutSelector).first()
      .isVisible().catch(() => false);
    if (out) throw new LoginRequiredError(this.name);
    return;
  }

  const input = page.locator(this.config.inputSelector).first();
  const visible = await input.isVisible().catch(() => false);
  if (!visible) throw new LoginRequiredError(this.name);
}
```

Two strategies. The good one: a `loggedOutSelector` — a "Log in" button that is
only present when you aren't. Nine of the ten browser providers configure one.
The fallback: if the prompt box isn't visible, assume logged out.

The fallback is a guess, and it is wrong in both directions. A site that is
merely slow to render produces a spurious `LoginRequiredError` telling you to
run `wspr login`, when the session was fine. A site that shows a prompt box to
logged-out visitors — and several do, gating only on submit — passes the check
and then fails later in a much more confusing place.

`.catch(() => false)` on the visibility probe means a detached element or a
navigating page reads as "not visible", which routes into the same guess.

## Submitting

```ts
const input = page.locator(this.config.inputSelector).first();
await input.waitFor({ state: "visible", timeout: 15000 });
await input.click();
await input.fill(prompt);

if (this.config.sendSelector) {
  await page.locator(this.config.sendSelector).first().click();
} else {
  await input.press("Enter");
}
```

`.first()` everywhere. If a selector matches three elements, the driver takes
one and never tells you the other two existed — which is how a selector that is
*almost* right produces behaviour that is confusingly wrong rather than an
error.

`fill()` sets the value in one operation rather than typing character by
character. It is far faster and far more reliable than `type()`, and it is also
the least human-looking thing the driver does: a real person does not
materialise 400 characters into a box instantaneously. Nothing here simulates
typing cadence.

Empty `sendSelector` means press Enter. Five of the ten providers use Enter —
including `qwen`, one of the two verified ones. The 15-second `waitFor` is the
only hard-coded timeout in the file that isn't configurable per provider.

## Flattening a conversation

When the whole history is sent — only on `newChat`, see
[§3.2](../3-api/3.2-choosing-a-model.md#conversation-state-is-not-symmetric) —
it becomes one prompt:

```ts
protected flatten(messages: Message[]): string {
  if (messages.length === 1) return messages[0].content;
  return messages.map((m) =>
    `${m.role === "user" ? "User" : m.role === "assistant" ? "Assistant" : "System"}: ${m.content}`
  ).join("\n\n");
}
```

A single message passes through untouched — no `User:` prefix — which is the
common case and the right special case. Multi-message histories get role labels,
which the model reads as text rather than as structure. A system prompt sent
this way is a line in a message beginning `System:`, with none of the weight a
real system role carries. There is no way to send a true system prompt to a
browser provider, because chat websites don't expose one.

## Counting before and after

```ts
const before = await this.countResponses(page);
await this.submitPrompt(page, prompt);
yield* this.streamAnswer(page, before);
```

`responseSelector` is documented in `providers.yaml` as matching **every**
assistant message block. The driver counts them before sending, then waits for
the count to exceed that number — that new element is the answer, and
`.last()` reads it.

This is a good design for a hostile problem: it needs no ids, no message
tracking, and no assumption about the site's DOM beyond "a new node appears per
answer". It has one failure mode, and it is severe. If `responseSelector` also
matches the **user's** turn, the count increments the moment your own prompt
renders — before the model has said a word — and `streamAnswer` immediately
starts reading `.last()`, which is your own question. It stabilises in two
seconds and returns your prompt back to you as the answer.

That is the single most likely symptom of a mis-specified provider, and it is
why `providers.yaml`'s comment on `pi` goes out of its way to record that
`div.text-body-alt-m.whitespace-pre-wrap` is used *only* by Pi's assistant
turns.
