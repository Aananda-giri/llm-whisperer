# 2.1 The path of a request

> **Status:** Implemented — traces code as it exists in `src/`.

Eight source files, ~1,290 lines. This page walks a single request through all
of them.

```
src/
  cli.ts             168  argv, startup, the login flow, shutdown
  config.ts          146  find + parse + validate providers.yaml, read env
  server.ts          351  express app: four routes, three request dialects
  browser.ts          83  launches ONE browser, hands out one context
  session-pool.ts     77  hands out pages from that context, with a queue
  providers/
    factory.ts        32  which class does this provider get
    base.ts          280  the contract, and the browser implementation
    api.ts           151  the HTTP implementation
```

## Startup

`wspr serve` (`src/cli.ts:36`) does four things in order:

```ts
const browser = new BrowserManager(config.profilesDir, config.headless, config.browserChannel);
const pool    = new SessionPool(browser);
const app     = createServer(config, pool);
// ...
const server  = app.listen(config.port, ...)
```

`loadConfig()` ran first, at `src/cli.ts:33`. Note what is *not* happening here:
no browser is launched. `BrowserManager` only stores its arguments; the actual
Chromium launch is deferred until someone calls `.context()`, which nothing does
until a browser provider gets a request. See
[§6.2](../6-operating/6.2-startup-and-environment.md#lazy-by-default).

`createServer` calls `buildProviders(config, pool)` once
(`src/server.ts:40`) and closes over the resulting `Map<string, LLMProvider>`.
Every route looks providers up in that map. The map is built once and never
mutated, so **changing `providers.yaml` requires a restart.**

## One request, end to end

Take:

```bash
curl -N http://localhost:9777/v1/chat/completions \
  -d '{"model":"groq/llama-3.1-8b-instant","stream":true,"messages":[...]}'
```

1. **Auth.** `requireApiKey` (`src/server.ts:59`) checks `WSPR_API_KEY` if it is
   set, and is a pass-through no-op if it isn't.
   [§3.4](../3-api/3.4-embeddings-and-auth.md#the-auth-gate)
2. **Split the model string.** `const [providerKey, modelName] = model.split("/")`
   → `"groq"` and `"llama-3.1-8b-instant"`.
   [§3.2](../3-api/3.2-choosing-a-model.md)
3. **Look up the provider.** `providers.get("groq")` → an `ApiLLMProvider`.
   A miss is a 400 that lists every configured key.
4. **Validate.** `messages` must be a non-empty array. That is the entire
   request validation in this codebase.
5. **Stream.** SSE headers, `flushHeaders()`, then `for await (const delta of
   llm.stream(messages, { newChat, model: modelName }))`, wrapping each delta in
   an OpenAI `chat.completion.chunk`. [§3.3](../3-api/3.3-streaming.md)
6. **Inside `stream()`** — for Door A, one `fetch` to
   `${baseUrl}/chat/completions` with `stream: true`, and `parseSSE` turns the
   upstream body back into deltas. For Door B, a page is acquired from the pool
   and the DOM is polled. [§4.1](../4-api-key-providers/4.1-one-class-many-services.md),
   [§5.1](../5-browser-providers/5.1-the-generic-driver.md)

The non-streaming path is the same up to step 5, where it calls `llm.chat()`
instead — which is itself just "run `stream()` and concatenate"
([§2.3](./2.3-the-provider-contract.md#one-abstract-method)).

## The shape of it

```
                    ┌──────────── src/server.ts ────────────┐
  HTTP request ────▶│ /chat  /v1/chat/completions           │
                    │ /v1/embeddings  /v1/messages          │
                    └───────────────┬───────────────────────┘
                                    │  providers.get(key)
                    ┌───────────────▼───────────────────────┐
                    │  Map<string, LLMProvider>              │  built once,
                    │  from buildProviders()                 │  at startup
                    └───────┬───────────────────┬───────────┘
                            │                   │
              cfg.api set ──┘                   └── no cfg.api
                            │                   │
                 ┌──────────▼───────┐   ┌───────▼──────────────┐
                 │  ApiLLMProvider  │   │   WebLLMProvider     │
                 │  fetch() upstream│   │   Playwright page    │
                 └──────────────────┘   └───────┬──────────────┘
                                                │ pool.acquire(name)
                                        ┌───────▼──────────────┐
                                        │  SessionPool         │
                                        │  ≤2 pages / provider │
                                        └───────┬──────────────┘
                                                │ .context()
                                        ┌───────▼──────────────┐
                                        │  BrowserManager      │
                                        │  ONE shared browser  │
                                        └──────────────────────┘
```

Read left to right, the interesting property is that the four HTTP routes never
learn which branch they took. They hold an `LLMProvider` and call `stream()`.

## Errors

Two typed errors travel all the way up from the providers and become 401s:

| Error | Thrown by | Means |
|---|---|---|
| `LoginRequiredError` | `WebLLMProvider.ensureLoggedIn` | The saved session is gone or expired |
| `ApiKeyMissingError` | `ApiLLMProvider.stream` / `.embed` / `.resolveEnv` | The provider's `keyEnv` is unset |

Everything else becomes a 500 with `(err as Error).message` in the body and a
`console.error` on the server. There is no error taxonomy beyond that, and no
retry anywhere in the codebase.

Each of the three dialects renders those same two errors in its own JSON shape —
which is most of what [§3.1](../3-api/3.1-three-dialects.md) is about.
