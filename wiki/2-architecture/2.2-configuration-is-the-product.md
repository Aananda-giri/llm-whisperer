# 2.2 Configuration is the product

> **Status:** Implemented — `providers.yaml` and `src/config.ts` as they ship.

There are two ways to support eighteen model providers. One is eighteen
adapters. The other is one adapter and eighteen rows of configuration.
llm-whisperer took the second, and the evidence that it worked is that
`OVERRIDES` in `src/providers/factory.ts` is still empty
([§1.2](../1-idea/1.2-two-doors.md#which-door-a-provider-uses)).

```console
$ node -e "const y=require('js-yaml'),f=require('fs');
  const p=y.load(f.readFileSync('providers.yaml','utf8')).providers;
  const api=Object.entries(p).filter(([,c])=>c.api);
  console.log('total providers   :', Object.keys(p).length);
  console.log('api-key providers :', api.length);
  console.log('browser providers :', Object.keys(p).length - api.length);"
total providers   : 18
api-key providers : 8
browser providers : 10
```
<sub>Generated 2026-08-01. This is the truth; a table that disagrees with it is stale.</sub>

Eighteen providers, zero provider-specific code.

## Two shapes in one map

`providers.yaml` has a single top-level `providers:` map whose entries come in
two shapes. A Door B entry is selectors:

```yaml
  pi:
    url: "https://pi.ai/talk"
    requiresLogin: false
    newChatSelector: "button[data-testid='nav-new-chat']"
    inputSelector: "textarea[data-testid='chat-composer-textbox']"
    sendSelector: "button[data-testid='chat-composer-submit']"
    responseSelector: "div.text-body-alt-m.whitespace-pre-wrap"
    timeoutMs: 90000
    stabilizeMs: 1500
```

A Door A entry is four lines of HTTP:

```yaml
  groq:
    api:
      baseUrl: "https://api.groq.com/openai/v1"
      model: "llama-3.3-70b-versatile"
      keyEnv: "GROQ_API_KEY"
```

The presence of `api:` is the discriminator, and it changes which fields are
even required. `loadConfig` validates each shape separately
(`src/config.ts:104`):

| Shape | Required fields |
|---|---|
| `api:` present | `baseUrl`, `model`, `keyEnv` |
| `api:` absent | `url`, `inputSelector`, `responseSelector` |

Everything else has a default, applied by spreading over a base object so that
browser-typed fields always exist even on API providers, where they are never
read:

```ts
providers[name] = {
  url: "", inputSelector: "", responseSelector: "",
  requiresLogin: false, timeoutMs: 90000, stabilizeMs: 2000,
  ...cfg,
} as ProviderConfig;
```

So `timeoutMs` defaults to 90 s and `stabilizeMs` to 2 s
([§5.2](../5-browser-providers/5.2-knowing-when-it-stopped.md) is entirely about
those two numbers).

## Keys are never in the file

`keyEnv` names an environment variable; it does not hold a key. The lookup
happens per request, in `ApiLLMProvider.stream`:

```ts
const key = process.env[this.api.keyEnv];
if (!key) throw new ApiKeyMissingError(this.name, this.api.keyEnv);
```

This is why `providers.yaml` is safe to publish inside the npm tarball
([§6.4](../6-operating/6.4-pnpm-and-publishing.md#what-ships)) — it is shipped
to every user of the package, and it contains no secrets by construction, not
by discipline. Reading the key at request time rather than at startup also means
you can export a key into a running shell without restarting… though the server
process would need restarting anyway to see it, so in practice this buys
nothing. It is simply the safe order.

`baseUrl` may also contain `${VAR}` placeholders resolved from the environment
at request time — see [§4.1](../4-api-key-providers/4.1-one-class-many-services.md#the-cloudflare-problem).

## Where the file is found

`findProvidersFile` (`src/config.ts:77`) tries four candidates in order and
takes the first that exists:

1. an explicit argument to `loadConfig()` (nothing passes one today)
2. `$PROVIDERS_FILE`
3. `./providers.yaml` — resolved against the **current working directory**
4. `<package root>/providers.yaml` — the copy bundled in the tarball

Candidate 3 is the important one: dropping a `providers.yaml` next to wherever
you run `wspr` silently replaces the bundled roster entirely. It is not merged
with the bundled one — the first file found wins, whole. That is the supported
way to add a provider without forking, and the supported way to accidentally
lose seventeen of them.

## What the config layer deliberately doesn't do

- **No selector validation.** `inputSelector: "textarea"` and
  `inputSelector: "banana"` are equally acceptable at load time. A wrong
  selector is discovered at request time, as a timeout, 90 seconds later.
- **No key validation.** Startup only *warns* about missing keys
  (`src/cli.ts:54`) and starts anyway. A provider you never use should not stop
  the server.
- **No schema for `models:`.** An empty selector string is valid config, and
  ten of the eighteen providers ship exactly that — which is the subject of
  [§5.6](../5-browser-providers/5.6-model-switching.md).

The design bet is that config errors are cheap to fix and expensive to police,
and that the person editing selectors is the same person running the server with
`HEADLESS=false` open next to them
([§6.3](../6-operating/6.3-when-a-provider-breaks.md)).
