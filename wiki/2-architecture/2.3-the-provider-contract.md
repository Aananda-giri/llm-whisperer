# 2.3 The provider contract

> **Status:** Implemented — `src/providers/base.ts` as it ships.

Four HTTP routes, three request dialects, two completely different ways of
reaching a model, and exactly one interface between them:

```ts
export interface LLMProvider {
  readonly name: string;
  stream(messages: Message[], options?: ChatOptions): AsyncGenerator<string>;
  chat(messages: Message[], options?: ChatOptions): Promise<string>;
}
```

`Message` is `{ role: "user" | "assistant" | "system", content: string }` —
content is a **plain string**, always. Everything richer that arrives at the
edge (Anthropic content blocks, OpenAI multimodal arrays) is flattened before it
reaches a provider. That flattening is lossy and the loss is documented at
[§3.1](../3-api/3.1-three-dialects.md#what-gets-lost-at-the-edge).

## One abstract method

`BaseProvider` implements `chat()` in terms of `stream()`:

```ts
export abstract class BaseProvider implements LLMProvider {
  constructor(public readonly name: string) {}
  abstract stream(messages: Message[], options?: ChatOptions): AsyncGenerator<string>;

  async chat(messages: Message[], options: ChatOptions = {}): Promise<string> {
    let result = "";
    for await (const chunk of this.stream(messages, options)) result += chunk;
    return result;
  }
}
```

So a new provider type writes **one method**. Buffered responses are the
streaming path with the deltas glued back together, which means the two paths
cannot drift: any bug in `stream()` is a bug in `chat()` by construction.

It also means every non-streaming request pays the full streaming cost. On Door
A that is free — the upstream was going to stream anyway. On Door B it means a
`stream: false` request still polls the DOM for the entire generation before
returning anything, which is why browser-provider requests feel slow even when
they are not.

## Options

```ts
export interface ChatOptions {
  newChat?: boolean;   // start a fresh conversation before sending
  model?: string;      // switch model before sending
}
```

Two flags, and each one means something different per door:

| | Door A (`ApiLLMProvider`) | Door B (`WebLLMProvider`) |
|---|---|---|
| `newChat` | **Ignored.** The API is stateless; you always send full history. | Clicks "new chat" or reloads the page, wiping context. |
| `model` | Replaces the model id in the request body. Always works. | Clicks through the site's model picker. Works on 1 of 10 providers — [§5.6](../5-browser-providers/5.6-model-switching.md). |

`newChat` being a silent no-op on Door A is correct behaviour badly named: for
an API there is no conversation to reset. But it means the same request produces
genuinely different semantics on the two doors, and the caller cannot tell which
they got. This is the one place the "indistinguishable doors" story leaks, and
[§3.2](../3-api/3.2-choosing-a-model.md#conversation-state-is-not-symmetric)
covers the consequence.

## Capabilities are structural, not declared

There is no capability registry, no `supports()` method, no feature flags. The
one optional capability in the codebase is embeddings, and it is expressed as a
separate interface plus a type guard:

```ts
export interface EmbeddingProvider {
  embed(input: string | string[], model?: string): Promise<EmbeddingResponse>;
}

export function supportsEmbeddings(p: LLMProvider): p is LLMProvider & EmbeddingProvider {
  return typeof (p as Partial<EmbeddingProvider>).embed === "function";
}
```

`ApiLLMProvider implements EmbeddingProvider`; `WebLLMProvider` does not. The
`/v1/embeddings` route calls `supportsEmbeddings(llm)` and returns a 400 saying
so if the answer is no (`src/server.ts:225`).

This is worth pausing on, because it is the honest version of a pattern that is
usually dishonest. A capability *declared* in config can be declared the day
someone writes the recipe. A capability that is a `typeof x.embed === "function"`
check cannot be wrong — the method is there or it isn't, and TypeScript narrows
the type on the strength of it. There is no gap between "declared" and "works"
because there is no declaration. See
[§8.2](../8-about/8.2-vocabulary.md#declared-vs-works).

The cost is that the pattern doesn't scale: a second optional capability needs a
second interface and a second guard, and a *partially* working capability has
nowhere to live. For one capability it is exactly right.

## The escape hatch nobody needed

```ts
const OVERRIDES: Record<string, new (...args: ConstructorParameters<typeof WebLLMProvider>) => WebLLMProvider> = {
  // e.g. chatgpt: ChatGPTProvider,
};
```

`WebLLMProvider`'s methods are `protected`, not `private`, specifically so a
subclass can override `submitPrompt`, `streamAnswer`, `ensureLoggedIn` and the
rest for a site that config can't describe. Ten browser providers in, the map is
still empty.

Two readings, and the book will not pretend to know which is right:

- The config abstraction genuinely covers the space, and the hatch is
  insurance well designed enough never to be claimed.
- Only two of the ten providers have actually been run end to end
  ([§5.5](../5-browser-providers/5.5-what-is-verified.md)), and the hatch is
  empty because the hard cases haven't been *attempted* yet.

The second is the more likely explanation for at least some of the eight. When
`chatgpt` gets a real end-to-end run and its Cloudflare interstitial needs
handling, this is where that code will go.
