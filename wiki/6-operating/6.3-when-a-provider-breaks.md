# 6.3 When a provider breaks

> **Status:** Implemented — the errors and the repair loop described here are
> what the shipped code produces.

Browser providers break. Not "might break" — a chat website ships a redesign
every few weeks, and every redesign is a coin flip on whether
`responseSelector` still matches. This page is what that looks like and what to
do about it.

## Reading the failure

Six failures cover nearly everything:

| Symptom | Almost certainly |
|---|---|
| `LoginRequiredError` — *"Not logged in to X. Run: wspr login X"* | Session expired, **or** `loggedOutSelector` now matches something it shouldn't |
| `X: timed out waiting for a response to start` + a screenshot | `responseSelector` no longer matches, or the prompt never got submitted |
| Times out after 15 s with a Playwright locator error | `inputSelector` no longer matches |
| **The answer is your own question** | `responseSelector` matches user turns too — [§5.1](../5-browser-providers/5.1-the-generic-driver.md#counting-before-and-after) |
| The answer stops mid-sentence, reported as complete | `timeoutMs` hit while still generating — [§5.2](../5-browser-providers/5.2-knowing-when-it-stopped.md#the-silent-truncation) |
| The answer is complete but a chunk is missing from the middle | Non-incremental re-render broke the append-only assumption — [§3.3](../3-api/3.3-streaming.md#in-door-b-polling-a-web-page) |

The last two are the dangerous ones, because they return HTTP 200 with
`finish_reason: "stop"` and look exactly like success.

## Start with the screenshot

The one timeout that throws leaves evidence:

```
qwen: timed out waiting for a response to start
      (url=https://chat.qwen.ai/, screenshot=/tmp/qwen-timeout.png)
```

Open it. It usually answers the question outright — a cookie banner covering the
composer, a Cloudflare interstitial, a logged-out landing page, a region block,
a "you've hit your limit" modal. None of those are selector problems, and all of
them look like selector problems from the server logs.

The screenshot is written on a best-effort basis (`.catch(() => {})`), so a
crashed page produces the error message without the file.

## The repair loop

Every browser provider is pure configuration
([§2.2](../2-architecture/2.2-configuration-is-the-product.md)), so a break is
fixed in YAML with no rebuild and no code.

**1. Watch it fail.**

```bash
HEADLESS=false wspr serve
```

Send the request and watch the window. Where it stops tells you which selector
died — nothing happens in the box (`inputSelector`), the prompt goes in but
nothing sends (`sendSelector`), the answer appears on screen but the API times
out (`responseSelector`).

**2. Find the new selector.** Devtools on the live page. Prefer, in order:

- `data-testid` attributes — the most stable thing a frontend gives you. `pi`'s
  four selectors are all `data-testid`, which is why `pi` is the least fragile
  provider in the file.
- Stable element ids — `ernie` falls back to `#eb_chat_viewer` for this reason.
- `aria-label` and role text — survives styling changes, breaks on
  translation. `grok` uses `button[aria-label='Submit']`.
- Substring class matches like `[class*='phase-answer']` — what `qwen` needed
  once its build started hashing class names.
- Exact class names — last resort. CSS-module builds regenerate these on every
  deploy.

**3. Check the response selector against a *user* turn.** The single most
important check, and the easiest to skip. In the devtools console:

```js
document.querySelectorAll("YOUR_SELECTOR").length
```

Run it on a conversation with three exchanges. If the answer is 6, the selector
is matching both sides and the provider will return your own prompt. You want 3.

**4. Edit `providers.yaml`, restart, retry.** Selectors take comma-separated
fallbacks, and most providers ship them:

```yaml
inputSelector: "textarea#chat-input, textarea[placeholder*='Message'], textarea"
```

Playwright takes the first match of the whole list, so order from most specific
to most general.

**5. Write down what you ran.** A fixed selector you watched work is
live-verified; a fixed selector that merely looks right is not
([§8.2](../8-about/8.2-vocabulary.md#live-verified-vs-recond)). Update the
provider's comment in the YAML and its row in
[§5.5](../5-browser-providers/5.5-what-is-verified.md). The distinction is only
worth anything if it is maintained.

## Editing the right file

If you installed from npm, the bundled `providers.yaml` lives inside
`node_modules` and an upgrade will overwrite it. Copy it out:

```bash
cp "$(npm root -g)/llm-whisperer/providers.yaml" ./providers.yaml
wspr serve     # ./providers.yaml in the CWD wins automatically
```

Or point `PROVIDERS_FILE` at it. Remember that your copy **replaces** the
bundled roster whole rather than merging with it
([§2.2](../2-architecture/2.2-configuration-is-the-product.md#where-the-file-is-found)).

## Failures that are not selectors

- **Rate limits and challenges.** Aggressive use gets you a Cloudflare
  challenge or a cooldown. The fix is fewer requests, not a better selector.
  [§1.3](../1-idea/1.3-terms-of-service.md) is the context.
- **Expired sessions.** `wspr login <name>` again, with `serve` stopped.
- **Profile lock.** *"Could not open the browser"* on `wspr login` means
  `serve` is still running ([§5.3](../5-browser-providers/5.3-sessions-and-login.md#the-lock)).
- **A model that was retired.** Door A only: an upstream 404 with the provider's
  own message attached ([§4.1](../4-api-key-providers/4.1-one-class-many-services.md#errors)).
  One line of YAML.

## When config isn't enough

If a site needs behaviour rather than selectors — dismissing a modal before
every send, handling an interstitial, a two-step submit — that is what the
`OVERRIDES` map in `src/providers/factory.ts` is for. Subclass
`WebLLMProvider`, override the one `protected` hook you need, register it.

The map is still empty ([§2.3](../2-architecture/2.3-the-provider-contract.md#the-escape-hatch-nobody-needed)).
`chatgpt`'s Cloudflare handling is the most likely first entry.
