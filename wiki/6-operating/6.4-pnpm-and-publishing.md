# 6.4 pnpm and publishing

> **Status:** Reference — package tooling, not a claim about the server's
> behaviour. Facts about `package.json` are current as of 0.1.5.

This chapter absorbs what used to be `wiki/pnpm.md`.

## Why pnpm

pnpm stores packages in a content-addressable global store (`~/.pnpm-store`) and
hard-links them into each project, instead of copying files into every
`node_modules`.

```
npm    →  copies files into every project's node_modules
yarn   →  same (v1), or PnP (v3+)
pnpm   →  hard-links from a global store
```

For this project specifically: Playwright and its dependencies are large, so
repeat installs are dramatically faster and the disk cost is paid once.

The other reason is **strictness**. pnpm's nested layout blocks *phantom
dependencies* — packages your code imports without declaring. npm's flat,
hoisted layout makes them accidentally importable, and they break the moment a
transitive dependency changes. Under pnpm they fail immediately with `Cannot
find module`, which is the error you want.

| npm | pnpm |
|---|---|
| `npm install` | `pnpm install` |
| `npm install <pkg>` | `pnpm add <pkg>` |
| `npm install -D <pkg>` | `pnpm add -D <pkg>` |
| `npm uninstall <pkg>` | `pnpm remove <pkg>` |
| `npm run <script>` | `pnpm run <script>` |
| `npx <cmd>` | `pnpm exec <cmd>` |
| `npm publish` | `pnpm publish` |

Nothing about the *published package* requires pnpm — it installs with `npm
install -g llm-whisperer` like anything else. pnpm is a development choice.

## The workspace file exists to say "no"

```yaml
# pnpm-workspace.yaml
packages: []
allowBuilds:
  esbuild: true
```

`packages: []` declares this directory its own workspace root with no
sub-packages. That matters because this repository sits inside a larger
directory of unrelated projects: without the file, a `pnpm-workspace.yaml` in
any parent would capture llm-whisperer as a member, deduplicate its installs
against the parent's, and pull in versions it never asked for.

An empty workspace is not a workspace feature being used. It is a fence.

`allowBuilds: esbuild: true` permits `esbuild` to run its native post-install
step, which pnpm blocks by default — a sensible default, since post-install
scripts are an obvious supply-chain surface.

`package.json` carries the same idea in newer syntax:

```json
"pnpm": {
  "ignoredBuiltDependencies": ["@anthropic-ai/claude-code"],
  "onlyBuiltDependencies": ["puppeteer-extra-plugin-stealth"]
}
```

`onlyBuiltDependencies` is an allowlist: **only** `puppeteer-extra-plugin-stealth`
may run install scripts. Every other dependency's are skipped.

## What ships

```json
"files": ["dist/", "docs/", "wiki/", ".env.example", "providers.yaml", "README.md"]
```

Six entries. `node_modules/`, the TypeScript sources, `tsconfig.json`, `.env`
and the `profiles/` directory are all excluded — the first two automatically,
the rest by omission from this list.

Two consequences:

- **`providers.yaml` ships to every user**, which is why it can never contain a
  key ([§2.2](../2-architecture/2.2-configuration-is-the-product.md#keys-are-never-in-the-file)).
- **`wiki/` ships**, so this book is inside the npm tarball. That is why
  [§8.1](../8-about/8.1-how-this-book-is-written.md) treats it as a published
  artifact rather than a scratch directory.

> The old `wiki/pnpm.md` listed this array without `.env.example`. It was
> correct when written and had quietly drifted — a hand-kept copy of a
> generated fact, which is the exact failure
> [§8.1](../8-about/8.1-how-this-book-is-written.md#2-generated-beats-hand-kept)
> is about. Check it rather than trusting this paragraph:
>
> ```bash
> node -e "console.log(require('./package.json').files)"
> ```

Preview the tarball before publishing:

```bash
pnpm pack --dry-run
```

## Publishing

```bash
npm login            # or pnpm login — same registry
pnpm publish --access public
```

`--access public` is required for unscoped packages when the account defaults to
private. `prepublishOnly` runs `tsc` before every publish, so stale `dist/`
output cannot ship:

```json
"prepublishOnly": "node node_modules/typescript/bin/tsc -p tsconfig.json"
```

It invokes the compiler by path rather than as `tsc`, which avoids depending on
whether the binary is on `PATH` under whichever package manager is running it.

The version in `package.json` and the published one currently agree:

```console
$ node -e "console.log(require('./package.json').version)"
0.1.5
$ npm view llm-whisperer version
0.1.5
```
<sub>Checked 2026-08-01.</sub>

There is no `test` script and no test files — `npm test` fails with "missing
script". The only automated gate on a publish is TypeScript compiling
([§1.1](../1-idea/1.1-what-it-is.md#shape-of-the-thing)).

## Before you publish, check the book

```bash
pnpm run check:wiki      # → node wiki/check.mjs
```

Because `wiki/` ships, a broken link in this book is a broken link in the
published package. The checker is 0-dependency Node and takes under a second;
what it does and does not verify is [§8.1](../8-about/8.1-how-this-book-is-written.md#what-is-checked-and-what-is-not).
