# 6.2 Startup and environment

> **Status:** Partial — everything here is implemented, but `WSPR_WARM` and the
> lazy-browser default exist **only in the uncommitted working tree** as of
> 2026-08-01. Published 0.1.5 warms tabs eagerly and has no `WSPR_WARM`.
> [§7](../7-status.md) tracks it.

The complete environment reference — every variable, every default — is
[`docs/configuration.md`](../../docs/configuration.md). This page covers what
`wspr serve` actually does at startup and the one behaviour that recently
inverted.

## Lazy by default

Published 0.1.5 opens a browser at startup. It calls `warmProviders()`
unconditionally, which pre-opens a tab for every browser provider that has a
saved session. The intent was a faster first request.

The problem, stated in the author's `todo`:

> Don't open browser in startup, e.g. starting server to use api, opening
> browser does not make sense

Someone running llm-whisperer purely for Groq and Gemini got a Chromium window
they had no use for. The working tree inverts it:

```ts
if (config.warmTabs) {
  await warmProviders(config, pool);
} else {
  console.log("Browser tabs launch on first use (set WSPR_WARM=true to pre-open them at startup).");
}
```

```ts
warmTabs: (process.env.WSPR_WARM ?? "false").toLowerCase() === "true",
```

So now:

| | Browser at startup? |
|---|---|
| `wspr serve` | **No.** Launches on the first browser-provider request. |
| `WSPR_WARM=true wspr serve` | Yes — one tab per logged-in browser provider. |

Nothing else was needed to make this work, because `BrowserManager` was already
lazy: it stores its arguments in the constructor and launches only when
`.context()` is first awaited
([§2.1](../2-architecture/2.1-path-of-a-request.md#startup)). The eager warm was
the *only* thing forcing a launch. Removing that call is the entire feature —
which is a good sign about where the laziness lived.

API-key providers never trigger a browser at all, at any point, in either mode.

### What warming actually does

```ts
const page = await pool.acquire(name, DEFAULT_BROWSER_PROFILE);
await page.goto(cfg.url, { waitUntil: "domcontentloaded", timeout: 30000 }).catch(() => {});
pool.release(name, DEFAULT_BROWSER_PROFILE, page);
console.log(`  ✓ ${name} ready`);
```

Worth reading the `.catch(() => {})`: a navigation that fails is swallowed, and
`✓ <name> ready` prints anyway. The tick means "a page object exists", not "the
site loaded" and certainly not "you are logged in". Only a `pool.acquire` throw
produces the `✗` branch.

Warming skips API providers, providers pinned to a named profile (those launch
lazily), and any login-requiring provider without a `.logged-in` sentinel —
the sentinel's only use in the codebase
([§5.3](../5-browser-providers/5.3-sessions-and-login.md#what-the-sentinel-is-used-for)).

## The environment, in brief

| Variable | Default | Notes |
|---|---|---|
| `PORT` | `9777` | WSPR on a keypad |
| `HEADLESS` | `false` | Note: **false** by default — you see the browser |
| `WSPR_BROWSER_CHANNEL` | bundled Chromium | `chrome` needed for Google OAuth logins; legacy `BROWSER` accepted only when it names a known Playwright channel |
| `WSPR_WARM` | `false` | Working tree only |
| `WSPR_BROWSER_PROFILE` | `default` | Default profile for logins and requests ([§5.3](../5-browser-providers/5.3-sessions-and-login.md)) |
| `PROFILES_DIR` | `~/.config/llm-whisperer/profiles` | Sessions + sentinels |
| `PROVIDERS_FILE` | bundled, or `./providers.yaml` | [§2.2](../2-architecture/2.2-configuration-is-the-product.md#where-the-file-is-found) |
| `CDP_URL` | unset | Attach to a running Chrome instead of launching |
| `WSPR_API_KEY` | unset | Unset ⇒ **no authentication** ([§3.4](../3-api/3.4-embeddings-and-auth.md#the-auth-gate)) |
| `<PROVIDER>_API_KEY` | — | One per API provider, named by `keyEnv` |

Two parsing details that behave unusually:

```ts
headless: (process.env.HEADLESS ?? "false").toLowerCase() !== "false",
```

Anything that is not the exact string `false` means headless. So `HEADLESS=0`,
`HEADLESS=no` and `HEADLESS=off` all turn headless **on** — the opposite of what
they read like. `WSPR_WARM` uses the safer inverse (`=== "true"`), where only
`true` enables it.

```ts
browserChannel: resolveBrowserChannel(),
```

`WSPR_BROWSER_CHANNEL=chromium` is normalised to `undefined`, meaning
Playwright's bundled build — not a channel lookup for a system Chromium. That is
the intended behaviour and the reason a system-installed `chromium` package
cannot be selected by name. The legacy `BROWSER` variable is honoured only when
it names a known Playwright channel (`chrome`, `msedge`, …) — desktop
environments often export `BROWSER` as a launcher command (e.g.
`omarchy-launch-browser`, `xdg-open`), which is ignored.

## The startup banner

```
       🤫
  l l m - w h i s p e r e r
  one quiet API for every LLM

listening on http://localhost:9777
Providers: qwen, deepseek, chatgpt, claude, glm, kimi, minimax, grok, pi, ernie, openai, gemini, groq, openrouter, cerebras, mistral, cloudflare, digitalocean
Profiles:  /home/you/.config/llm-whisperer/profiles
Browser tabs launch on first use (set WSPR_WARM=true to pre-open them at startup).
```

The provider list is every configured key, in YAML order, with no indication of
which door each uses or which have credentials. Eighteen names, of which — on a
fresh install with one Groq key — exactly one will answer.

## Shutdown

`SIGINT` and `SIGTERM` both run the same handler: close the HTTP server, close
the browser (flushing profiles to disk), `process.exit(0)`. `server.close()` is
not awaited, so in-flight responses are cut rather than drained
([§5.4](../5-browser-providers/5.4-the-session-pool.md#shutdown)).

Ctrl-C during an active browser conversation loses that conversation's tab
state. The login cookies survive; the open chat does not.
